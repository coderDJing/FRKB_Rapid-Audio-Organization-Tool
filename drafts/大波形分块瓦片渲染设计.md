# 大波形分块 / 瓦片渲染设计

## 文档定位

本文是 detail 大波形渲染架构升级的设计与接手文档，供**新会话自包含接手**。

阅读顺序：

1. **先读** `drafts/双轨和编辑模式大波形体验与架构标准.md`（大波形宪法：owner 规则、Stable Frame 规则、
   禁止回退项、一票否决项）。本文不重复其内容，只在冲突点显式引用。
2. 再读本文。

**本文不是 bug 修复文档**，是架构升级。它对应架构标准第 146 行早已指出、但尚未实施的方向：
「下一步是更重的架构方向：预构建 linked replacement frame、把 worker stable frame 渲染做成
**可抢占 / 增量**，或让 linked 开启前就持有可直接切换的双 deck 对齐 frame。」

## 为什么要做

不是为了修某一个卡顿，而是解开当前架构里一个**结构性死结**：

> **覆盖范围（overscan 要大）与单次重绘成本（面积要小）被绑定在同一个尺寸上。**

当前 detail 大波形把整个可视区 + 左右 overscan 渲染成**一张超宽位图**。后果：

- **overscan 越大越安全，但每次重绘越贵**。而重绘触发点很多：seek、缩放、改 BPM、改网格、
  播放滚动超出 overscan、双轨联结 / BeatSync 的 replacement frame。
- **overscan 用尽就漏空波形**。真机已确认：把位图上限压到 4096 后，「拖动大波形左滑，后面一下就漏出
  空波形」。现状只能靠「把 overscan 开得足够大」掩盖，这又推高上面每一笔重绘成本。
- **位图物理宽 11823px 超过 GPU 单纹理上限**（硬件普遍保证的最小值 8192），无法作为单一纹理。
- **双 buffer 各持一张超宽位图**常驻显存。

分块把两者解耦：**要覆盖更远就多挂几块，而不是把单张画得更大。** 收益覆盖 seek / 缩放 / 联结 /
BeatSync / 拖拽等所有重绘路径，而不只是 tempo 松手。

## 现状实测事实（勿重新测量）

来自阶段性真机诊断记录：

| 项 | 值 |
| --- | --- |
| viewport CSS 宽 | ≈ 965 px |
| devicePixelRatio | ≈ 1.75 |
| 渲染宽（含左右 overscan）CSS | ≈ 6756 px |
| 位图物理宽 | ≈ 11823 px |
| **可见面积占渲染面积** | **≈ 14%（即 86% 是屏幕外 overscan）** |
| overscan 档位 | `min(max(256, vw*3), maxOverscan)`，左右**对称** |

**卡顿与位图面积正相关**（同机同操作，promote 时的 RAF 空档）：

| 位图物理宽 | 松手 promote 空档 |
| ---: | ---: |
| 11823px | 82~132ms |
| 8000px | 82~115ms |
| 4096px | 48~81ms（均 66ms） |

→ 面积减半，卡顿几乎减半。**这组数据是分块方案有效性的量化依据**：若只需先合成可见区（≈1/7 面积），
按比例外推约 **15ms**，一帧内可完成。

相关常量与函数：

- `horizontalBrowseCanvasGeometry.ts`：`STABLE_MAX_RENDER_SCALED_WIDTH = 15360`（位图物理宽上限）、
  `resolveHorizontalBrowseStableOverscanCssPx`。
- `horizontalBrowseStableCanvasPresentation.ts`：`resolveHorizontalBrowseStableCanvasOffsetCssPx`
  （末尾 `Math.round(rawOffset * pixelRatio) / pixelRatio` 做整数物理像素量化）、
  `canPresentHorizontalBrowseStableCanvas`、`measure/apply/tickPlayback/handleRendered`。
- `horizontalBrowseLiveCanvasBuffers.ts`：双 buffer（front/back）与 `activate` opacity 翻转。

## 核心设计

### 关键前提：改 BPM / 缩放会让**所有**块失效

改 BPM 或缩放会改变**整个波形的时间密度**，因此不存在「只有部分块需要重画」。

> **分块的收益不来自「少画几块」，而来自「先画用户看得见的那几块」。**

因此本设计的核心是**优先级调度**，而不仅是把位图切开。滚动场景下才有真正的「块复用」
（平移时大部分块内容不变）。

### 渲染优先级：三档（含播放方向预取）

参考 Rekordbox 的可观察行为（从播放头向后渲染、超出屏幕后再回头向前补充），并按 FRKB
「播放头在屏幕 50%」的事实收紧：

| 档 | 范围 | 时机 | 用户可感知 |
| --- | --- | --- | --- |
| **P0** | **整个可见区**（播放头两侧，≈965 CSS px） | 必须**全部 ready 才切换可见面** | 是 |
| **P1** | 前向 overscan（播放前进方向 / 未来时间） | P0 之后，随后数帧内 | 否（屏幕外） |
| **P2** | 后向 overscan（已播过 / 过去时间） | 最后 | 否（屏幕外） |

**为什么 P0 必须整块齐了才切换**：架构标准「一票否决项」明确禁止
「拖拽大波形时出现不可解释的空白、断层」「近距离 beat 跳转触发不可解释的空白」；
「禁止回退项」也记录过 `displayReady=true` 保旧面曾造成**波形缺块**。
因此 FRKB 要比 Rekordbox 更严：**允许屏幕外缺块，不允许可见区缺块。**
P0 未齐时，按现有 `preserveSurfaceUntilNextReady` 语义**继续显示旧可见面**（这与架构标准
第 140~142 行一致），而不是露白。

**收益仍然成立**：必须等的面积从 7/7 降到 1/7。

### 非对称 overscan（本设计新增结论）

当前 overscan 左右**对称**，但**播放只朝一个方向推进**——后向 overscan 在稳态播放期基本闲置。
分块后应按方向分配：**前向多、后向少**。

- 稳态播放：前向块池更深，保证滚动不触底；后向保留少量块用于小幅回拖。
- 用户反向拖动时：按需追加后向块（P1/P2 优先级动态互换）。

净效果：总常驻面积下降，而滚动流畅度不降。

### 瓦片划分与接缝（最高风险点）

- **划分方向**：仅**横向**切块（时间轴方向）。纵向不切——高度就是一个 lane 的高度。
- **块宽**：建议以 viewport 宽为基准的固定 CSS 宽（如 `viewportWidth` 或其 1/2），使 P0 恒为 1~2 块。
- **像素对齐（必须）**：块边界必须落在**整数物理像素**上，否则会出现接缝（缝隙或 1px 错位）。
  现有 `resolvePixelSnappedCssSize` 与 offset 的 `Math.round(* pixelRatio) / pixelRatio` 量化逻辑
  必须扩展到「每块的起始 x」，且**相邻块的结束 x 与下一块起始 x 必须严格相等**（用累计整数像素推进，
  不要各块独立 round，否则会累积漂移）。
- **波形采样连续性**：每块按自己的时间范围采样波形时，块边界处的采样窗口必须与相邻块**无缝衔接**
  （不能各自向内取整导致边界处少画或重画一列）。这是接缝的第二个来源，比几何对齐更隐蔽。
- **高 DPI**：架构标准一票否决项含「高 DPI 或系统缩放下波形明显发虚或粗细跳变」。多块必须在
  dpr = 1 / 1.25 / 1.5 / 1.75 / 2 下逐一验证无接缝、无粗细差异。

### 块池与回收

- 维护一个**块池**（复用 canvas / OffscreenCanvas 与其纹理），避免每次滚动都新建销毁。
- 每块记录：`rangeStartSec`、`rangeDurationSec`、`timeScale`（密度）、`renderRevision`、`ready`。
- **失效判定**：`timeScale` 或 `renderRevision` 变化 → 全部块内容失效（见上文前提）；
  仅平移 → 仅缺失方向的块需要新渲染，其余按几何平移复用。
- **回收策略**：超出「可见区 + 前向池 + 后向池」范围的块归还池中，优先复用最远的块。

### 与双 buffer promote 流程的整合

当前是 front/back 两张超宽 canvas，promote 时 `activate(index)` 翻转 opacity 完成整屏切换。
分块后建议：

- **保留双缓冲语义**，但粒度从「整张」变为「块集合」：新一代（新 timeScale / revision）的块渲染到
  备用块集合，**P0 全部 ready 后**一次性切换可见集合（与现有 `handleRendered` → `activate` 的时机对应）。
- `resolveHorizontalBrowseStableCanvasOffsetCssPx` 现在返回单张位图的 translate；分块后应改为
  **块集合的统一平移量 + 每块自身的布局 x**。建议保持「统一 translate 挂在块容器上」，
  这样 `tickPlayback` 的滚动路径改动最小（仍是给一个容器写 translate3d）。
- **CSS tempo scale（`.tempo-scaler`）应挂在块容器上**，而非每块——否则每块各自缩放会在边界处产生
  亚像素错位（本轮 jitter 调查中，两 buffer 独立 scaler 已被验证不是 bug 源，但分块后每块独立 scaler
  会引入新的接缝风险）。

### overlay 层不分块（降风险）

**只把波形层分块，overlay 层（播放头、cue、loop、grid 线与标签）保持单层。**

理由：overlay 是线条与文字标记，重绘成本低；而**文字标签跨块切割极易出接缝/重影**。
保持单层可绕开这一整类问题，且不损失主要收益（波形位图才是面积大头）。

## 红线与风险

必须遵守架构标准的既有约束，以下条目与本设计**直接相关**：

- **可见区不得出现不可解释空白**（一票否决项）。分块引入的缺块只允许发生在屏幕外。
- **不得为了波形先稳定而影响声音**（一票否决项 / 禁止回退项）。分块是纯视觉改动，不得触碰
  native transport、播放时钟、seek。
- **`preserveSurfaceUntilNextReady` / `preserveDisplay` 语义不得被削弱**（架构标准 140~142 行）：
  P0 未齐时必须真正保留旧可见面（含 stable playback 与 presentation frame），
  不能只保留 DOM opacity。
- **旧帧 handoff 规则不变**（143 行）：旧帧按自身 `viewportRangeStartSec / anchorSec / playbackRate`
  推进，不能把新 viewport 套到旧帧上。
- **不得提交常驻 trace 型落盘日志**（禁止回退项 158 行）。调试用诊断按当轮复现临时加，提交前清理。
- **不得只修当前 deck**（160 行）：必须同时检查另一条 deck、overview、overlay、theme、DPI、编辑模式。

新增风险：

- **接缝类问题偶发且难复现**（依赖 dpr、缩放比例、块边界落点）。必须在多 dpr / 多缩放级别下系统性验证。
- **块数增加带来的合成层管理成本**。若块数过多，合成层数量本身可能成为新瓶颈——
  注意本轮已验证「减少常驻 will-change 层」对单层面积瓶颈无效，但块数量级变化后需重新评估。
- **编辑模式深度 zoom**（一票否决项 347 行要求细节足够）：深 zoom 下块数会显著增加，需验证不退化。

## 分阶段实施（全程 feature flag）

**要求**：全程挂在 feature flag 后，flag 关闭即完全走现有超宽单张路径，可随时回退。
每阶段独立真机验收，通过后再进入下一阶段——避免像 tempo jitter 那轮在一个大改动里连追十几轮。

| 阶段 | 内容 | 验收 | 状态 |
| --- | --- | --- | --- |
| 1 | 引入瓦片抽象与块池，flag 关闭时行为**完全不变** | 现有全部大波形行为无回归（对照一票否决项清单） | 代码完成 |
| 2 | **暂停态**分块渲染（不含滚动） | 视觉与现状一致；多 dpr / 多缩放级别**无接缝**；编辑模式深 zoom 细节足够 | 代码完成，**待真机验收** |
| 3 | 播放滚动 + 块复用回收 + 非对称 overscan | 滚动流畅；**快速拖动不漏空波形**；overview / overlay / grid 不错位 | 代码完成，**待真机验收** |
| 4 | P0/P1/P2 优先级调度 + tempo 松手 / seek / 缩放路径 | 松手无 >40ms RAF 空档；seek / 缩放无空白闪烁 | 代码完成，**待真机验收** |
| 5 | 移除 flag 与旧超宽路径 | 全量回归 + 推荐手测流程 | **未开始**（须等 2~4 验收通过，否则失去回退能力） |

### 已实现的落点（阶段 1~4）

flag：`horizontalBrowseWaveformTileFlag.ts`，**默认开启**。回退只需把 `let tileRenderingEnabled = true`
改成 `false`；关闭时块容器一行 style 都不会被写入，该等价性由
`horizontalBrowseWaveformTileBuffers.spec.ts` 机器断言。

新增纯逻辑模块（均有 spec）：

- `horizontalBrowseWaveformTileLayout.ts` —— 全局网格几何、块时间范围、P0/P1/P2 分档。
- `horizontalBrowseWaveformTilePool.ts` —— 块池复用 / 失效 / 回收（匹配键 `(generation, globalIndex)`）。
- `horizontalBrowseWaveformTilePlan.ts` —— 把几何与块池编排成可执行渲染计划。

接线改动：块容器 div（每 buffer 一个，位于 `.tempo-scaler` 之内）承载 `left / width / transform`，
与旧单张超宽 canvas 语义完全一致，故 presentation offset、rendered viewport 反解均未改公式，
只把类型从 `HTMLCanvasElement` 放宽到 `HTMLElement`。worker 侧 `renderWaveformTiles` 复用同一个
`drawRange`，波形外观与旧路径同源。

### 实施中确认的三条现状约束（与原设计假设不符，已按此调整）

1. **canvas 控制权移交是一次性的**（`transferControlToOffscreen`），运行期无法追加画布。
   故块划分改为**固定块数**（8）而非固定块宽，`maxTileCount = 块数 + 1` 是与位图宽 / dpr 无关的常量。
2. **块边界必须锚定全局网格，不能按当前位图等分**。等分取整会让块宽互不相等
   （11823÷8 → 1478,1478,1477,1479…），该宽度序列不具平移不变性，平移后无一块能命中上一轮结果，
   滚动复用会整体失效。全局网格（原点 = 歌曲 0 秒，块宽恒定）下平移只是「换几个 globalIndex」。
   代价是位图两端各有不足一块的溢出，由块容器 translate 吸收、外层 `overflow:hidden` 裁掉。
   此问题由「平移后只需重画缺口方向」的单测在实现早期直接暴露（预期复用 6 块、实得 3 块）。
3. **非对称 overscan 改由优先级调度承担**，几何仍保持左右对称。把几何做成非对称会让可见区不再
   居中于渲染范围，牵动 presentation offset 与播放头对齐的整套换算（含 tempo 过渡期旧帧 handoff），
   收益仅是少画一两块屏幕外块，不值该风险。前向块先补、后向块最后补已达到同样的稳态效果。

### 与阶段 3/4 时序相关的实现要点

- **块计划随渲染请求同一条消息下发**（`renderRequest.tilePlan`），而不是独立消息。worker 先画完
  P0 才回报 `rendered`，因此 `rendered` 到达即意味着可见区就绪，promote 时序天然正确，
  主线程无需做双路异步汇合。
- **屏幕外块（P1/P2）在 rendered 之后逐帧续画**，每帧一块，避免一次性长任务再次造成掉帧；
  补齐后以 `renderViewportOnly: true` 回报，只用于登记块池 ready，不触碰可见面。
- **可见区未齐时回报 `ready: false`**，走现有 `preserveSurfaceUntilNextReady` 语义保留旧可见面。
- 分块路径下 worker 不再走整帧 preserve / 滚动复用（`resetFrameState()`），因为超宽位图已无波形内容。

## 验收标准

除架构标准的「验收标准」与「一票否决项」全部适用外，本项目专属：

- 松手 / seek / 缩放时，RAF 帧间隔**不再出现 > 40ms 空档**（这是本轮 jitter 调查用的判定方法：
  逐帧记录 `performance.now()` 差值）。
- 拖动大波形（含快速左右滑）**任何时刻不漏出空波形**。
- 多 dpr（1 / 1.25 / 1.5 / 1.75 / 2）下**无接缝、无粗细跳变**。
- 双轨联结 / BeatSync 下上下 deck grid 严格对齐，无临时错位。
- 声音无任何卡顿 / 爆音 / 变速。

## 已证伪路径（勿重试）

来自 tempo jitter 那轮真机验证，与本设计相关：

- **压小 overscan / 位图上限换取性能** —— 会漏空波形，已否决。
- 减少常驻 `will-change` 合成层数量 —— 对单层面积瓶颈无效。
- 时钟相位重锚、IPC / worker 侧优化、位置几何修正 —— 均与合成开销无关。
