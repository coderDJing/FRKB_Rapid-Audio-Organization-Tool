# 歌曲分析全局并发策略

## 1. 目标

所有歌曲分析入口共用同一个 `KeyAnalysisQueue` 和同一份并发额度。手动批量、当前可见列表、
waveform preview 与后台任务只能提交 job；它们不得各自创建 worker、drain 队列或拥有独立并发上限。

这样做的目的，是在提高人工批量分析吞吐的同时，始终把播放、切歌与波形交互放在前面。

## 2. 当前策略

全局并发范围固定为 1 到 2 路：

- 默认 1 路。
- 只有存在待分析数量大于 1 的手动批量任务、没有正在播放的 deck，且最近 5 秒没有
  `preparePlayhead`、seek 或切歌等 transport 操作时，才提升到 2 路。
- 任一 deck 开始播放、出现 transport 操作、手动批量不再有足够待处理项时，都重新评估并收回到 1 路。
- 后台闲时分析仍受 `BACKGROUND_MAX_INFLIGHT = 1` 保护，不能因全局上限是 2 就抢占前台资源。

策略由 `src/main/services/keyAnalysisQueue.ts` 统一计算并调用队列的运行时并发调整；不需要重建
每个任务的队列。

## 3. 不变量

- 并发额度属于全局队列，不属于 batch、歌单、窗口或任意入口。
- 优先级只决定下一份额度优先处理哪个 job，不增加总 worker 数。
- 不能按 CPU 核数直接扩到 3 路或更多。分析链路还会占用解码、FFmpeg、Python runtime、缓存写入和 UI 事件。
- 不得为批量任务单独开 worker，或让多个入口各自 drain 队列；这会让总负载随任务数量线性增长。
- 不得为追求吞吐削弱播放、seek 或当前 deck 的优先级。

## 4. 验收边界

- 多个手动批量并发提交时，实际 worker 总数仍不超过 2。
- 播放、切歌或 seek 后，分析应及时回到单路，前台 transport 不应因批量分析而被抢占。
- 手动批量完成或取消后，不得遗留额外 worker、重复 job 或卡住的队列状态。
- 后台任务不能绕过 `BACKGROUND_MAX_INFLIGHT`。

代码修改时需覆盖队列归属、动态升降级和播放/transport 触发的回归测试；不要把一次运行时日志
当成策略正确性的唯一证据。
