# FRKB 库合并维护与安全约束

维护状态：已实现，持续维护

创建日期：2026-07-12

本文约束已实现的 FRKB 库合并功能。它记录长期用户语义、数据安全边界和验收要求；具体实现、表字段、界面文案和某次任务日志以当前代码为准。

## 1. 用户语义

- 只支持 **FRKB 库合并到当前打开的 FRKB 库**；当前库永远是目标，用户只选择来源库。
- 支持“复制并合并”和“合并后删除来源库”。删除模式不是边复制边删除，来源只会在目标成功提交后才清理。
- 普通歌单同名时不覆盖，也不把两份内容混在一起。来源歌单以 `名称 (from 来源库名)` 加序号的方式保留。
- 合并不做跨库歌曲去重，不因文件名、hash 或元数据相同而悄悄丢弃来源曲目。
- 合并是独占任务。任务期间当前库不能进行其它写入；必须提供真实阶段进度和可恢复的结束状态，不能用普通 toast 假装完成。

## 2. 开始前必须全部通过

- 来源必须由有效 `FRKB.database.frkbdb` manifest 识别，且与目标不是同一库、也不互相嵌套。
- 来源 SQLite 必须能只读打开并通过完整性、外键、schema 和库树校验。无法识别的来源结构、文件类型、业务表或数据参与者一律拒绝，禁止跳过后报告成功。
- 目标没有未完成合并或恢复锁；来源和目标都不能有会写库或库文件的活动任务。独立 Mixtape 窗口等绕开主窗口锁的写入入口也必须先关闭。
- 预检必须按真实待复制内容、SQLite/WAL 增量、暂存和安全余量计算目标卷可用空间。无法可靠取得容量或空间不足时不得创建任务和写入文件。

## 3. 原子性与恢复

合并不是复制整个目录，更不能覆盖来源 SQLite。正确的提交顺序固定为：

```text
只读预检 → 持久化任务和锁 → 复制到目标隐藏暂存区 → 校验并提升媒体
→ 单次 SQLite 事务写入目标数据 → 记录已提交 →（删除模式）清理来源 → 解锁
```

- 目标正式 SQLite 只能在提交事务中修改；事务提交前失败时，当前库必须保持合并前状态。
- 媒体提升和数据库提交之间的窗口必须由持久化任务日志覆盖。下次启动要能辨认未提交任务并清理，或辨认已提交任务并完成收尾。
- 来源删除发生在提交标记之后。删除失败是“目标合并成功、来源待清理”的部分成功，绝不能反向破坏目标库。
- 清理只能针对已验证的来源根及计划内路径；不能用计算出的宽泛路径、递归猜测或当前库回收站替代来源清理。

## 4. 数据迁移边界

- 库树节点必须重建目标 UUID，并通过不可变的 UUID、相对路径和绝对路径映射重写引用；禁止复制来源 UUID、SQLite 文件或通过字符串替换路径。
- 完整库合并覆盖普通歌单、Set、Mixtape 和录音库的受支持业务数据。Set/Mixtape 的项目、item、cue、网格及相关引用必须按映射重建；派生 stem 状态可失效并从 `pending` 重建。
- 曲目分析数据只有在目标媒体身份可验证后才迁移。封面、波形、display waveform、stem 和外部设备分析等可重建缓存不从来源复制。
- 目标库自身 `meta` 不得被来源覆盖；只有登记过合并函数的元数据才可合并。新增持久化表或元数据必须先加入数据参与者合同，否则合并应 fail closed。
- 回收站内容不导入。来源没有被明确支持的内容不能静默忽略。
- 精选库合并是范围更小的独立模式；它只能按该模式的受支持数据与来源清理边界执行，不能假装等同于完整库合并。

## 5. 用户可见要求

- 用户不需要在开始前逐项处理曲目或歌单冲突；预检用于安全判断，不是差异预览。
- 进度按扫描、复制、校验、数据库提交和来源清理等实际阶段表达。复制阶段显示真实字节或文件量，不能虚构稳定的全局百分比或剩余时间。
- 成功页说明导入数量、自动改名数量、迁移的可保留数据，以及来源是否已清理。任何部分成功必须明确说明，不得显示为完全失败或完全成功。

## 6. 维护与验收

改动合并功能时，至少验证：

1. 空间不足、来源损坏、嵌套根目录、schema 不兼容、未知数据参与者和活动写入任务都能在写入前拒绝；
2. 同名歌单、大小写路径冲突、Set/Mixtape 引用、录音重名和可迁移分析数据按合同处理；
3. 复制、校验、提升、SQLite 提交和来源删除每个阶段中断后，重启都能安全恢复；
4. 删除模式不会在目标提交前修改来源，目标成功后来源清理失败也不会回滚目标；
5. 浅色/深色主题下的锁定、进度、错误和完成状态可读，且不允许任务期间绕过锁继续写库。

不以一次普通成功合并替代这些故障路径验证。合并功能的通过标准是：用户得到完整、可继续使用的目标库，来源在用户选择保留或删除的边界内受到保护。
