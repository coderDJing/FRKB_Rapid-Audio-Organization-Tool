# 双轨对拍听感跑马问题草案

维护状态：主因已修复；主输出保护第一版待真实试听

更新时间：2026-07-29

## 文档定位

本文记录一个不能仅用“网格线看起来对齐”判定通过的双轨问题：同一对歌曲在 Rekordbox 的双轨模式开启 BeatSync 后能稳定自动对拍；在 FRKB 的双轨模式开启联结或 BeatSync 后，网格线看似对上，但听感存在明显的跑马、鼓点发虚或难听。

本文是持续维护的诊断与验收草案，不是修复完成说明。结论按证据等级分层：只有经过真实 PCM 对照和代码链路核验的项目才写为“已确认”；其余只保留为风险或待验证项。

## 本次样本与现象

| 项目 | 结论 |
| --- | --- |
| 对照来源 | FRKB 自己的 `test` 歌单，与 Rekordbox 的“未命名列表”中的同两首歌 |
| 歌曲 | DHEA（134 BPM MP3）与 VERMILLION（135 BPM） |
| Rekordbox | 双轨开启 BeatSync 后自动对拍，听感正常 |
| FRKB | 开启联结或 BeatSync 后，显示网格可对齐，但两首 kick 叠加有约 25 ms 的固定错位，听感像跑马 |
| 网格定义 | 两首都是固定 BPM、单 clip 网格；不是动态段落切换，也不是 BPM 倍率数学累计漂移 |

## 已确认主因：FRKB 丢失 DHEA 的解码时间原点

### 事实

- DHEA 的网格首拍时间为 `0.426807s`。
- 该 MP3 的正确 `timeBasisOffsetMs` 为 `25.057ms`；正确的 PCM 首拍应落在 `0.426807 - 0.025057 = 0.401750s`。
- 本机这首歌的持久化数据中 `timeBasisOffsetMs` 缺失（`null`）。Renderer 将缺失值强制传为 `0`，见 `src/renderer/src/composables/horizontalBrowse/horizontalBrowseNativeTransport.ts:126`，双轨提交分别见 `:156`、`:168`。
- native transport 同样把缺失值解释为 `0`，并按 `audioSec = timelineSec - timeBasisOffsetSec` 读取 PCM，见 `rust_package/src/horizontal_browse_transport_dynamic_grid.rs:21-31`。
- 因而 FRKB 的同步数学是在同一个“虚拟网格时间线”上算对的，但 DHEA 实际播放的 PCM 相对该时间线提前约 `25.057ms`；与另一轨对齐后，真正听到的 kick 没有对齐。
- 用 `25.057ms` 补回 DHEA 时间基后，两轨实测鼓点都落在约 `204.5ms`，证明这不是仅凭代码推测的候选原因。

### 为什么网格线一致仍然会难听

```text
网格时间线首拍：     0.426807 s
缺失 offset 后的音频：0.426807 s 被当成 PCM 位置
真实 PCM 首拍：       0.401750 s
固定差值：            25.057 ms（约 0.05596 beat / 20.15°）
```

这说明“网格点相同”只证明网格数据相同；它不能证明 grid timeline 与解码 PCM timeline 的原点相同。对 kick 这类瞬态，约 25 ms 已足以让两首歌叠起来明显跑马。

若 DHEA 以 134 BPM 追随 135 BPM，墙钟上的这项偏差约为 `25.057 / (135 / 134) = 24.871ms`，仍是明显可闻的量级。

### 已排除的主因候选

- BeatSync 的固定 BPM 速率数学正确：134 BPM 按 `135 / 134` 播放后，两轨每秒都前进 `2.25 beat`；10 分钟浮点模拟误差约 `0.0000296ms`，不能解释听感跑马。
- 两首都是单 clip 固定网格，动态追速平滑器不会介入。
- 原生 `alignToLeader` 的最近拍相位求解逻辑本身正确，位于 `rust_package/src/horizontal_browse_transport_engine_state.rs:394-418`。

### 缺失值为何会在“重新导入并重新分析”后出现

已确认不是分析器漏算：当前 BPM 分析持久化在没有传入 offset 时会探测并写入 `timeBasisOffsetMs`。实际丢失发生在随后打开本地实体歌单的目录扫描：

- `analysisOnly` 曲目扫描时先从文件重新构造基础元数据，再从缓存继承分析结果。
- 原先 `preserveCachedGridAnalysisFields()` 只继承了 `beatGridMap`，遗漏同一时间基契约里的 `timeBasisOffsetMs` 和 `beatGridAlgorithmVersion`。
- 扫描末尾会用缺字段的对象回写 SQLite；因此一次正常“打开/刷新歌单”就能把刚分析好的 offset 覆盖掉。

2026-07-29 已修复：扫描会将 offset、算法版本与 v2 map 一并继承。扫描 worker 只负责目录/缓存读取；缺失或可疑 MP3 零值的时间基回填在主进程执行，避免 worker 找不到 bundled ffprobe 时错误写入 `0`。打开 `test` 歌单后，DHEA 与 VERMILLION 会自动进入回填路径。

真实回归：DHEA 曾以 `0ms` 提交给 native；修复后主进程回填 `25.057ms`，双轨 `set-deck-state` 与 `set-state` 均确认收到 `25.057ms`。用户复听确认跑马听感明显改善。

## 可能放大听感的次级问题

这些问题不推翻上述主因；应在补齐时间基后再独立验收。

### SoundTouch 的局部瞬态抖动

- 90 秒输出帧数与理论值一致，未发现累计 BPM 漂移。
- 真实音频测得的局部偏移：DHEA `134 -> 135` 平均 `+2.46ms`、P95 绝对偏移 `6.75ms`、最大 `8.5ms`；VERMILLION `135 -> 134` 平均 `-1.72ms`、P95 `7ms`。
- transport 强制开启 SoundTouch QuickSeek，位置为 `rust_package/src/horizontal_browse_transport_audio.rs:39`。QuickSeek 是以质量换速度的模式，可能令瞬态略发虚，但它解释不了本次稳定的约 25 ms 固定错位。

### 双轨混音硬削波

- crossfader 居中时两轨均为 unity gain，见 `rust_package/src/horizontal_browse_transport.rs:860-866`；总线随后直接裁剪到 `[-1, 1]`，见 `:604-616`。
- 对齐后的这两首真实音频模拟中，follower 为 unity 时峰值 `1.528`，约 `2.72%` 样本被削平；follower 衰减 `1dB` 时仍有 `1.70%` 样本削平。
- 削波不会制造固定相位差，但会把已经错开的双 kick 变得更刺耳，因此属于“难听”的放大器。

2026-07-29 已实现第一版主输出保护：两轨 program 信号先在立体声联动 peak limiter 中处理，阈值 `-1 dBFS`、上限 `-0.3 dBFS`、瞬时压低和约 `80ms` release；录音使用同一份限幅后的 program 总线。这样不改变用户的通道音量、三频 EQ、crossfader 或 Auto Gain 语义。CUE/节拍器仍不进入录音；它们与 program 合成后的物理输出另经无状态软保护，避免重新出现平顶硬削波。

为便于真实观察，`LIMIT` 已移至右上角总音量旋钮左侧，并按 `50ms` 刷新：上下两条分别展示限幅前的真实 L/R program peak，黄线为 `-1dBFS` 预警、最右侧红线为 `-0.3dBFS` 上限。两条从左侧蓝色开始，仅靠近右端才渐变为黄/红；数字显示两声道联动 limiter 共享的当前 gain reduction（dB）。横条跳动但未到红端，表示音频确实到达总线但未需要保护；压限数字才表示 limiter 实际参与。待以 DHEA / VERMILLION 的中心位叠放和录音文件进行真实试听验证。

2026-07-31 已做 SoundTouch A/B 试听并确认：仅将双轨实时 Master Tempo 的 `QuickSeek` 加速模式关闭；Master Tempo、变速对拍、网格和同步数学均保持不变。真实样本的 30 秒、44.1kHz 立体声基准显示关闭后处理耗时增加约 `15.7%–16.6%`，但仍为约 `15.6–15.8x` 实时，具备性能余量。DHEA / VERMILLION 在 `134 -> 135` 和 `135 -> 134` 两方向的实际试听已确认效果可接受。

### 联结起播与后续状态刷新风险

- 联结起播目前按 leader、follower 顺序发送两次 `setPlaying`，不是单次原子双轨启动，见 `src/renderer/src/composables/horizontalBrowse/useHorizontalBrowseDeckPlaybackController.ts:932-933`。这可能带来调度相关的小偏差，但不可能稳定复现为 DHEA 的 `25.057ms`。
- `refresh_sync_state(true)` 有机会调整 `current_sec`；若该调整发生在 SoundTouch 已初始化之后而未重置其处理状态，下一批声音可能仍从旧处理状态输出。显式 `BeatSync` / `alignToLeader` 会重置并预热 Master Tempo，见 `rust_package/src/horizontal_browse_transport_engine_state.rs:932`，故不是本次首次对拍的主因。
- 联结开启时，只要两轨 snapshot 都报告 `syncEnabled && syncLock === 'full'` 就跳过实际校相，见 `src/renderer/src/composables/horizontalBrowse/useHorizontalBrowseFaderControls.ts:172-190`。若先前音频已经错位，此快路径会保留错误状态。
- 未解码完成时，原播放流程和 ready watcher 都可能再次触发播放，见 `useHorizontalBrowseDeckPlaybackController.ts:918-949` 与 `:1043-1051`。这是条件性竞态，当前没有证据表明它是本次固定症状的来源。

## 修复顺序

1. 修复并补齐所有音频（优先 DHEA/MP3）的 `timeBasisOffsetMs` 生成、持久化、载入与 native transport 传递；缺失值不可再静默伪装成 `0` 后参与双轨同步。
2. 针对已有库数据，设计可验证的回填/重新分析路径，并确保歌曲网格 timeline、cue 和 PCM decode timeline 使用同一份时间基契约。
3. 以这两首歌做真实双轨 PCM 与耳听回归：联结、单轨 BeatSync、暂停后 BeatSync 再开播、切换 master、拖拽/seek 后再对拍。
4. 在主因通过后，分别处理原子双轨起播、SoundTouch 状态刷新重置和 `syncLock === 'full'` 快路径健康检查。
5. 最后单独评估交叉推子中心的混音 headroom / soft limiter，不能把削波问题伪装成“对拍问题已修复”。

## 验收门槛

- 同一对样本中，FRKB 补齐时间基后的双轨 kick 必须与正确 PCM 基准对齐；不能只看 UI 网格重合。
- 在 134/135 两个方向上，连续播放至少 90 秒不得出现累计相位漂移；局部 SoundTouch 瞬态误差与固定时间基错位须分开量化。
- 联结与 BeatSync 都要覆盖：初次启动、暂停后恢复、切主轨、拖拽、seek、开启/关闭联结。
- 双轨中心混音不得因硬削波掩盖相位结论；需同时记录峰值与削波样本比例。
- 以 Rekordbox 的同曲双轨结果作为听感参照，但 FRKB 的通过判定必须包含实际 PCM 时间轴验证，不能把“Rekordbox 看起来正常”当作 FRKB 的替代证据。

## 维护规则

- 新证据必须标出样本、音频格式、`timeBasisOffsetMs`、网格首拍、比对方式和是否为真实 PCM 结果。
- 不得将“网格线一致”写成“声音已对齐”。
- 不得把 SoundTouch、削波或状态机风险升级为本次主因，除非在正确时间基下仍能稳定复现并有对应 PCM/日志证据。
- 修复前后都要保留同曲、同位置、同 BPM 方向的可复核对照；不要用换歌后的主观听感替代回归。
