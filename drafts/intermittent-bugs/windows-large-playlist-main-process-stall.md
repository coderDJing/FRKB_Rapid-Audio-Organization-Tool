# Windows 大歌单主进程卡顿：已解决事故记录

## 状态

- 状态：`已解决`；
- 首次记录：2026-08-06；
- 结案依据：用户确认问题已修复；
- 影响范围：Windows 打开千首级筛选库歌单时，主进程曾短暂无响应。

本文保留根因和修复边界，防止后续优化时把同类问题重新引入；它不是当前现场排查手册。

## 已确认根因

问题电脑的一次真实现场中，worker 扫描 1224 首仅耗时约 2.9 秒，但主进程在创建时间基修复任务时连续阻塞约
20 秒。旧实现通过 `songs.map(async ...)` 加 `Promise.all` 构造任务；每个 async 回调在首次 `await` 前都会
同步调用 `execFile(ffprobe.exe)`，于是 Windows 主线程无界启动大量子进程。

这不是 renderer 列表掉帧或 IPC 送达慢。磁盘、Defender 或其他安全软件可能放大子进程创建成本，但不改变
“歌单打开链路不能无界启动 FFprobe”的根因和修复要求。

## 保留的修复不变量

1. 歌单打开链路只负责扫描与修复规划，不能等待整批 FFprobe 或缓存回写；
2. 时间基修复必须进入全局后台队列；任务函数入队前不得提前启动子进程；
3. 每批 FFprobe 最大并发为 4；
4. Windows 上的 FFprobe 探测及子进程创建必须在专用 worker thread 中执行，不能只把 Promise 留在 Electron
   主线程；
5. 缓存回写使用原子 `json_set` 更新 `timeBasisOffsetMs` 和 `timeBasisOffsetAlgorithmVersion`，不得以扫描时
   的整首旧对象覆盖 `info_json`，以免覆盖随后发生的网格编辑；
6. 合法零偏移也必须持久化算法版本标记。否则跨进程重启后会被误认为未修复，重复触发 FFprobe；
7. 后台完成后通过既有 `song-grid-updated` 逐首更新当前歌单，而不是阻塞首屏响应。

## 为什么零偏移版本标记不可省略

现场批次中，1224 首候选只有 168 首得到非零偏移。若只把“偏移不为零”视为已完成，其他合法零偏移歌曲会在
每次重启后重新探测，重新放大大歌单打开时的 Windows 子进程创建压力。完成状态必须由
`timeBasisOffsetAlgorithmVersion` 表示，而不是由偏移数值推断。

## 若未来再次出现类似卡顿

先读取 `log.txt`，用同一 `traceId` 关联 `playlist-scan-diagnostic` 与 `main-process event loop stalled`，确认
卡顿是否仍处在时间基后台修复阶段。只有同时出现“主响应未先返回”“后台并发超过 4”“主线程直接创建 FFprobe”
之一时，才按本事故回归处理；否则应把它当作新的卡顿链路排查，不要先入为主归因到 FFprobe。

现有诊断日志是为偶发回归保留的运行时证据。除非有新的问题现场或用户明确要求，不增加常驻 trace，也不恢复
一次性的排查日志。
